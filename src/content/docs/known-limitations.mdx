---
title: Known Limitations
description: Behaviors in kumolo that differ from real AWS by design or as a known gap.
---

kumolo aims for high fidelity, but some behaviors differ from real AWS by design or as a known gap.

## S3

**Bucket Policy and ACL are not enforced**

`PutBucketPolicy`, `GetBucketPolicy`, `PutBucketAcl`, `GetBucketAcl`, `PutObjectAcl`, and `GetObjectAcl` succeed and persist the configuration.
However, kumolo does not evaluate the stored policy or ACL on subsequent requests — all requests are permitted regardless of their content.

**SigV4 signatures are not verified**

kumolo parses SigV4 headers and presigned URL parameters to extract request metadata (e.g., expiry time), but does not cryptographically verify the signature.
Any non-empty `aws_access_key_id` / `aws_secret_access_key` pair is accepted.
This is intentional for local development — you do not need to manage real credentials.

## DynamoDB

**`ConsumedCapacity` values are not computed**

`ReturnConsumedCapacity` is fully supported and `ConsumedCapacity` is included in responses when set to `TOTAL` or `INDEXES`.
However, kumolo always returns `CapacityUnits: 1.0` — actual RCU/WCU are not calculated.

**Number precision is limited to float64**

DynamoDB number attributes are internally stored and compared using `float64`.
Values with more than 15 significant digits may not sort or compare correctly.
Real AWS DynamoDB uses arbitrary-precision decimal arithmetic.

## STS

**`AssumeRole` does not simulate distinct roles**

`AssumeRole` always returns the same fixed credentials regardless of the `RoleArn` specified in the request.
If your code relies on different roles returning different permissions or identities, kumolo cannot simulate that behavior.
