kumolo implements the Cognito User Pools REST API. All operations accept standard AWS SDK v2 requests — point your client at `http://localhost:5566`.
Unlike S3, `UsePathStyle` is not required; only `BaseEndpoint` needs to be overridden on the client.

A JWKS endpoint is available at `http://localhost:5566/{userPoolId}/.well-known/jwks.json` for JWT verification.

## Support levels

| Symbol | Meaning                                                                                   |
| :----: | ----------------------------------------------------------------------------------------- |
|   ✓    | Fully implemented — the feature behaves like real AWS                                     |
|   ◐    | Partial support — the operation works but has known limitations; see the note for details |
|   —    | Not yet implemented                                                                       |

## Operation support

Operations sourced from [`internal/cognito/router.go`](https://github.com/optiflowic/kumolo/blob/main/internal/cognito/router.go) in the kumolo repository.

| `UpdateUserPool`              |     ◐     |
| `DeleteUserPool`              |     ✓     |
| `ListUserPools`               |     ✓     |
| `GetUserPoolMfaConfig`        |     ◐     |
| `SetUserPoolMfaConfig`        |     ◐     |
| `AddCustomAttributes`         |     —     |
| `GetLogDeliveryConfiguration` |     —     |
| `SetLogDeliveryConfiguration` |     —     |
| `GetSigningCertificate`       |     —     |

:::note
Password policy enforcement: kumolo enforces minimum length (default 8 characters), AWS's 256-character maximum length, and complexity rules (`RequireUppercase`, `RequireLowercase`, `RequireNumbers`, `RequireSymbols`, all default `true`) on every operation that accepts a plaintext password (`SignUp`, `AdminCreateUser`, `AdminSetUserPassword`, `RespondToAuthChallenge`'s `NEW_PASSWORD_REQUIRED`, `ConfirmForgotPassword`, `ChangePassword`). kumolo accepts and stores `PasswordHistorySize` but does not enforce it — no password history is tracked.

kumolo enforces `DeletionProtection`: `DeleteUserPool` rejects a pool with `DeletionProtection` set to `ACTIVE` (`InvalidParameterException`); unprotected pools remain deletable.

`GetUserPoolMfaConfig` / `SetUserPoolMfaConfig`: kumolo persists only `MfaConfiguration` (`OFF`/`ON`/`OPTIONAL`) — this is the pool-level enforcement switch, not a per-user record. `SoftwareTokenMfaConfiguration.Enabled` always reports as `false` since kumolo doesn't model this pool-level TOTP method toggle; this is independent of per-user TOTP enrollment, which is fully supported (see `AssociateSoftwareToken` / `VerifySoftwareToken` / `SetUserMFAPreference` below). kumolo accepts but silently ignores `SmsMfaConfiguration`/`EmailMfaConfiguration`/`WebAuthnConfiguration`. A pool with `MfaConfiguration: "ON"` forces every unenrolled user through the `MFA_SETUP` challenge on sign-in, and an enrolled user cannot disable MFA afterward — see `RespondToAuthChallenge` and `SetUserMFAPreference` below. `MfaConfiguration: "OPTIONAL"` is accepted but not enforced; only per-user `SetUserMFAPreference` opt-in applies in that case.

`AccountRecoverySetting` is accepted, stored, and returned as-is on `CreateUserPool` / `UpdateUserPool` / `DescribeUserPool`. `CreateUserPool` defaults it to `verified_phone_number` (priority 1) then `verified_email` (priority 2) when omitted, matching AWS. See `ForgotPassword` below for how it's consumed.
:::

| ----------------------------- | :-------: |
| `SignUp`                      |     ◐     |
| `ConfirmSignUp`               |     ✓     |
| `ResendConfirmationCode`      |     ◐     |
| `InitiateAuth`                |     ◐     |
| `RespondToAuthChallenge`      |     ◐     |
| `AdminInitiateAuth`           |     —     |
| `AdminRespondToAuthChallenge` |     —     |
| `ForgotPassword`              |     ◐     |
| `ConfirmForgotPassword`       |     ◐     |
| `ChangePassword`              |     ◐     |
| `GetTokensFromRefreshToken`   |     —     |
| `RevokeToken`                 |     ✓     |
| `GlobalSignOut`               |     ✓     |

`InitiateAuth` supports the following auth flows:

- `USER_PASSWORD_AUTH` — username and password authentication
- `USER_SRP_AUTH` — SRP-6a authentication (used by AWS Amplify by default)
- `REFRESH_TOKEN_AUTH` — exchange a refresh token for new tokens

`RespondToAuthChallenge` supports the `NEW_PASSWORD_REQUIRED`, `PASSWORD_VERIFIER`, `SOFTWARE_TOKEN_MFA`, and `MFA_SETUP` challenges.

:::note
**Confirmation codes**: codes issued by `SignUp` and `ResendConfirmationCode` are written to the kumolo server log instead of being sent via email or SMS. Use `AdminConfirmSignUp` in tests to skip code retrieval entirely.

**Token expiry**: `ExpiresIn` and each token's `exp` claim reflect the requesting client's `AccessTokenValidity`/`IdTokenValidity`/`RefreshTokenValidity`, honoring `TokenValidityUnits` (defaults: hours for access/ID tokens, days for refresh tokens, matching AWS). Expiry is enforced on every authenticated request.

**`SecretHash`, `ClientMetadata`, `AnalyticsMetadata`, `UserContextData`**: accepted on all auth operations but ignored. Lambda triggers are not supported.

**`RespondToAuthChallenge`**: `USERNAME` is optional in kumolo (taken from the session JWT when omitted); on real AWS it is required.

**`USER_SRP_AUTH` / `PASSWORD_VERIFIER`**: implements the SRP-6a protocol AWS Amplify uses by default, so Amplify apps can point at kumolo without switching to `USER_PASSWORD_AUTH`. An unknown username fails immediately with `UserNotFoundException` at `InitiateAuth` — kumolo does not implement AWS's anti-enumeration "fake verifier" response. A `FORCE_CHANGE_PASSWORD` user completing SRP authentication receives a chained `NEW_PASSWORD_REQUIRED` challenge instead of tokens, same as `USER_PASSWORD_AUTH`.

**`SOFTWARE_TOKEN_MFA`**: issued instead of tokens whenever `USER_PASSWORD_AUTH`, `PASSWORD_VERIFIER`, or the post-`NEW_PASSWORD_REQUIRED` reset succeeds for a user with TOTP MFA enabled (see `SetUserMFAPreference` below). `RespondToAuthChallenge` verifies the submitted `SOFTWARE_TOKEN_MFA_CODE` as a TOTP code (RFC 6238, ±1 time step / ±30s clock skew) against the user's registered secret; a mismatch returns `CodeMismatchException`. On success, tokens are issued exactly as for the non-MFA path.

**`MFA_SETUP`**: issued instead of `SOFTWARE_TOKEN_MFA`/tokens whenever primary authentication succeeds for a user with no TOTP secret registered (`TOTPSecret == ""`) in a pool with `MfaConfiguration: "ON"`. A user who already holds a registered TOTP secret gets `SOFTWARE_TOKEN_MFA` instead — even if `SoftwareTokenMFAEnabled` is currently `false` (e.g. a user who enrolled and then disabled MFA while the pool was still `OPTIONAL`, then the pool switched to `"ON"`): kumolo reuses the existing authenticator rather than forcing re-enrollment through a fresh secret, matching AWS's documented MFA decision tree. Completing that `SOFTWARE_TOKEN_MFA` challenge self-heals `SoftwareTokenMFAEnabled` back to `true`. `ChallengeParameters` reports `MFAS_CAN_SETUP: ["SOFTWARE_TOKEN_MFA"]` — only TOTP enrollment is offered, matching kumolo's overall MFA support. `REFRESH_TOKEN_AUTH` never re-triggers this challenge, and it never fires for `MfaConfiguration: "OPTIONAL"` pools. Complete enrollment with the Session-authenticated `AssociateSoftwareToken` / `VerifySoftwareToken` calls below, then call `RespondToAuthChallenge` with `ChallengeName: "MFA_SETUP"` and the verified `Session` — no `ChallengeResponses` beyond an optional `USERNAME` (must match the session's username if supplied) are required, since the verified secret already travels in the session. On success kumolo persists the TOTP secret, sets `SoftwareTokenMFAEnabled: true` and `PreferredMfaSetting: "SOFTWARE_TOKEN_MFA"`, and issues tokens. Responding with a session that never completed `VerifySoftwareToken` returns `NotAuthorizedException`.

**`ForgotPassword` / `ConfirmForgotPassword`**: like `SignUp`, kumolo writes the reset code to the server log (`ForgotPassword` message) instead of emailing or texting it — set `KUMOLO_LOG_LEVEL=debug` to see the code; the default `info` level logs the event without it. `ForgotPassword` selects the code delivery attribute using the user pool's `AccountRecoverySetting.RecoveryMechanisms` priority order — a pool without an explicit `AccountRecoverySetting` defaults to `verified_phone_number` (priority 1) then `verified_email` (priority 2), matching AWS's default. An `admin_only` recovery mechanism disables self-service recovery entirely. If the user has no verified attribute matching an eligible mechanism, kumolo returns `InvalidParameterException`, matching real AWS's requirement. kumolo does not implement code expiry (`ExpiredCodeException`), and does not enforce `PreventUserExistenceErrors` — a missing username always returns `UserNotFoundException`.

**`ChangePassword`**: kumolo does not apply password history policy (`PasswordHistoryPolicyViolationException`), and does not check the access token's OAuth scope.
:::

### User operations

| Operation                          | Supported |
| ---------------------------------- | :-------: |
| `GetUser`                          |     ✓     |
| `UpdateUserAttributes`             |     ◐     |
| `DeleteUserAttributes`             |     —     |
| `DeleteUser`                       |     ✓     |
| `GetUserAttributeVerificationCode` |     ◐     |
| `VerifyUserAttribute`              |     ◐     |
| `GetUserAuthFactors`               |     —     |
| `SetUserMFAPreference`             |     ◐     |
| `SetUserSettings`                  |     —     |
| `GetUICustomization`               |     —     |
| `SetUICustomization`               |     —     |
| `UpdateAuthEventFeedback`          |     —     |

:::note
`UpdateUserAttributes`: real AWS holds a new `email`/`phone_number` value pending until verified via `VerifyUserAttribute`. kumolo has no email/SMS delivery to gate on, so it applies every attribute change immediately. Changing `email`/`phone_number` still resets the paired `email_verified`/`phone_number_verified` attribute to `false` and generates a verification code (logged at Info level, same as `SignUp`).

`GetUserAttributeVerificationCode` / `VerifyUserAttribute`: `AttributeName` is restricted to `email` or `phone_number` — the only attributes kumolo tracks a verification code for.

`SetUserMFAPreference`: only `SoftwareTokenMfaSettings` is persisted; `SMSMfaSettings`, `EmailMfaSettings`, and `WebAuthnMfaSettings` are accepted but silently ignored. Setting `Enabled: true` without a prior successful `VerifySoftwareToken` call is rejected with `InvalidParameterException` — kumolo requires a registered TOTP secret before it can be made the sign-in requirement. Setting `Enabled: false` clears the preferred-MFA flag but keeps the registered TOTP secret, so re-enabling doesn't require another enrollment round trip — except in a pool with `MfaConfiguration: "ON"`, where disabling an already-enrolled user's MFA is rejected with `InvalidParameterException` instead: real AWS doesn't let users disable an MFA method once the pool requires MFA. Enabling remains allowed in an `"ON"` pool (e.g. pre-registering TOTP before ever signing in with MFA). This rejection only applies once the pool is already `"ON"`: disabling in an `OPTIONAL`/`OFF` pool is unconditionally allowed, and if the pool is later switched to `"ON"`, that user's stored TOTP secret still gets challenged directly via `SOFTWARE_TOKEN_MFA` on next sign-in rather than forcing a fresh `MFA_SETUP` enrollment (see `MFA_SETUP` above).
:::

### MFA & WebAuthn

| Operation                      | Supported |
| ------------------------------ | :-------: |
| `AssociateSoftwareToken`       |     ◐     |
| `VerifySoftwareToken`          |     ◐     |
| `StartWebAuthnRegistration`    |     —     |
| `CompleteWebAuthnRegistration` |     —     |
| `DeleteWebAuthnCredential`     |     —     |
| `ListWebAuthnCredentials`      |     —     |

:::note
`AssociateSoftwareToken` / `VerifySoftwareToken`: accept either `AccessToken` (an already-signed-in user enrolling MFA from a settings screen) or `Session` (completing a forced `MFA_SETUP` challenge from `InitiateAuth`/`RespondToAuthChallenge`, see above) — supplying both or neither returns `InvalidParameterException`. `AssociateSoftwareToken` generates a Base32-encoded TOTP secret (RFC 4648/6238); the AccessToken flow stores it as pending on the user record, while the Session flow carries it in the (kumolo-specific, signed-JWT) session instead — nothing is written to user storage until `RespondToAuthChallenge` completes. Calling it again before verifying discards the previous pending secret. `VerifySoftwareToken` checks the submitted 6-digit code against the pending secret (±1 time step / ±30s clock skew); on success the AccessToken flow promotes it to the user's active TOTP secret immediately (this only registers the authenticator — call `SetUserMFAPreference` to enable it for sign-in), while the Session flow returns a new session carrying the now-verified secret for the subsequent `RespondToAuthChallenge` call. A code mismatch returns `CodeMismatchException` (HTTP 400) rather than AWS's `Status: "ERROR"` response body.
:::

## Quick start

<Tabs>
  <TabItem label="Go">
    ```go
    package main

    import (
    	"context"
    	"fmt"

    	"github.com/aws/aws-sdk-go-v2/aws"
    	"github.com/aws/aws-sdk-go-v2/config"
    	"github.com/aws/aws-sdk-go-v2/credentials"
    	"github.com/aws/aws-sdk-go-v2/service/cognitoidentityprovider"
    	"github.com/aws/aws-sdk-go-v2/service/cognitoidentityprovider/types"
    )

    func main() {
    	cfg, err := config.LoadDefaultConfig(context.Background(),
    		config.WithRegion("us-east-1"),
    		config.WithCredentialsProvider(
    			credentials.NewStaticCredentialsProvider("test", "test", ""),
    		),
    	)
    	if err != nil {
    		panic(err)
    	}

    	client := cognitoidentityprovider.NewFromConfig(cfg, func(o *cognitoidentityprovider.Options) {
    		o.BaseEndpoint = aws.String("http://localhost:5566")
    	})

    	// Create a user pool
    	pool, err := client.CreateUserPool(context.Background(), &cognitoidentityprovider.CreateUserPoolInput{
    		PoolName: aws.String("my-pool"),
    	})
    	if err != nil {
    		panic(err)
    	}
    	userPoolID := pool.UserPool.Id

    	// Create a user pool client
    	appClient, err := client.CreateUserPoolClient(context.Background(), &cognitoidentityprovider.CreateUserPoolClientInput{
    		UserPoolId: userPoolID,
    		ClientName: aws.String("my-app"),
    		ExplicitAuthFlows: []types.ExplicitAuthFlowsType{
    			types.ExplicitAuthFlowsTypeAllowUserPasswordAuth,
    		},
    	})
    	if err != nil {
    		panic(err)
    	}
    	clientID := appClient.UserPoolClient.ClientId

    	// Sign up a user (confirmation code is logged to the kumolo server log)
    	_, err = client.SignUp(context.Background(), &cognitoidentityprovider.SignUpInput{
    		ClientId: clientID,
    		Username: aws.String("alice"),
    		Password: aws.String("P@ssw0rd!"),
    	})
    	if err != nil {
    		panic(err)
    	}

    	// Admin confirm so no code retrieval is needed in tests
    	_, err = client.AdminConfirmSignUp(context.Background(), &cognitoidentityprovider.AdminConfirmSignUpInput{
    		UserPoolId: userPoolID,
    		Username:   aws.String("alice"),
    	})
    	if err != nil {
    		panic(err)
    	}

    	// Authenticate
    	auth, err := client.InitiateAuth(context.Background(), &cognitoidentityprovider.InitiateAuthInput{
    		ClientId: clientID,
    		AuthFlow: types.AuthFlowTypeUserPasswordAuth,
    		AuthParameters: map[string]string{
    			"USERNAME": "alice",
    			"PASSWORD": "P@ssw0rd!",
    		},
    	})
    	if err != nil {
    		panic(err)
    	}
    	fmt.Println("AccessToken:", *auth.AuthenticationResult.AccessToken)
    }
    ```

    import boto3

    client = boto3.client(
        "cognito-idp",
        region_name="us-east-1",
        endpoint_url="http://localhost:5566",
        aws_access_key_id="test",
